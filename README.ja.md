# 日本の労働法令に対する RAG

*言語: [English](README.md) · [Русский](README.ru.md) · 日本語*

> 凍結した 50 問の golden で **recall@5 0.94** ・すべてローカルで実行（Ollama、Postgres + pgvector、GTX 1060）・採用しなかった設計はすべて数値を根拠に却下。

日本の労働法令コーパスを対象とした検索・回答システムです。「有給って入社してすぐもらえるの？」のような口語の質問に対し、根拠条文を明示して回答します。

ポートフォリオとして作成したものですが、計測については実務と同じ規律で進めました。**すべての改善は golden dataset 上の数値で裏付けられており、採用しなかった設計もすべて数値を根拠に却下しています。**

### 埋め込みモデルの入れ替え：BGE-M3 → Ruri-v3

再ランカーも質問拡張も使わない、コアスライス上の純粋なベクトル検索（同じ 50 問）：

| モデル | r@1 | r@5 | r@10 | r@20 | MRR |
|---|---|---|---|---|---|
| bge-m3 | 0.38 | 0.68 | 0.76 | 0.92 | 0.51 |
| multilingual-e5-large | 0.52 | 0.76 | 0.78 | 0.86 | 0.61 |
| **ruri-v3-310m** | **0.56** | **0.86** | **0.94** | **1.00** | **0.71** |

r@20 を併記しているのは、再ランカーが 20 件のプールを処理するためで、これが後段の上限になるからです。r@5 だけ見ると e5 が BGE-M3 を上回りますが、r@20 では下回ります。

全体構成：

| 構成 | r@5 | 秒/クエリ |
|---|---|---|
| bge-m3 + 拡張 + 再ランク | 0.86 | 15.6 |
| ruri-v3 単体 | 0.86 | 0.2 |
| **ruri-v3 + 再ランク** | **0.94** | 15.2 |
| ruri-v3 + 拡張 + 再ランク | 0.96 | 14.0 |

Ruri 単体でも、調整済みの BGE-M3 構成全体と同等です。採用したのは、質問拡張を**使わない** Ruri + 再ランカーです。拡張で増える 0.02 は 1 問分にすぎず、辞書はこの golden に対して作られた唯一の要素なので、この golden 上での効果は楽観的な値になります。0.94 はその偏りのない数値です。

生成側（同一プロンプト、BGE-M3 → Ruri）：コンテキスト再現率 0.88 → 0.94、引用による主張のカバー率 0.57 → 0.64、原文と一致する本文 0.62 → 0.68、項ラベルの誤り 3 → 0。採用構成ではプロンプトに 1 行（条番号は見出しの表記のまま書き写す）を追加しており、3 回の実行の平均は、主張カバー率 0.62、原文と一致する本文 0.64、項ラベルの誤り 1 件（#39、注意事項を参照）です。

### 逐語引用とコードによる検証

条文は正しいのに細部が誤っている、という失敗は引用マーカーでは検出できません。生成モデルには条文を「…」で逐語引用させ、コードがすべての引用を、引用元のチャンクと項に照らして検証します。採用構成（3 回の実行の平均）では、**主張の 0.62 が検証済みの引用でカバー**され、回答本文の 0.64 が原文と一致しました。この検証で、「正しい本文が別のマーカーの下にある」という最初の事例も自動的に見つかりました。

生成側（BGE-M3 の実行）では、引用形式の遵守が50件中50件、コンテキストに存在しない条文への言及は0件でした。Ruri の実行ではまだこの水準に達していません（注意事項を参照）。

## 画面

![画面](docs/screenshot.png)

UI は結果だけでなく**システムの動作**を見せることを目的にしています。右側には検索が返したすべての条文と再ランキングのスコアを並べ、回答が実際に使ったものを強調し、使わなかったものを淡く表示します。スクリーンショットは典型的な例で、提示した5条のうち使用は1条、スコアの差は一桁（0.768 対 0.054 以下）です。

回答中の `[1]` マーカーはクリックでき、各記述と根拠条文を結びつけます。回答可能／回答不可の判定はバッジとして表示します。これは文章から拾い上げた表現ではなく、モデルが1行目に必ず出力することを求められている項目です。

応答は SSE で逐次送られます。根拠条文は生成開始前、最初のイベントとして届きます。

画面は日本語とロシア語に対応しています。質問は常に日本語です。コーパスも埋め込みもプロンプトも日本語であるため、他言語の入力を受け付けるのは実態に反するからです。

## 構成

```
質問
  ↓ ベクトル検索（Ruri-v3-310m をプロセス内で実行 + pgvector HNSW、ef_search 200）  上位20
  ↓ 再ランキング（bge-reranker-v2-m3）             上位20 → 上位5条
  ↓ コンテキスト構成：各条文を全項まとめて投入
  ↓ 用語ヒント：質問の後に「日常語 → 法令用語」の対応を付ける【用語の対応】
  ↓ 逐語引用つきの引用規約による生成（gemma4:e4b）
  ↓ 出力ガード：リンクを許可リストと照合（ストリーミング途中でも）
回答 ＋ [N] マーカー ＋「回答可能／回答不可」の明示的な判定
```

以前のパイプライン（BGE-M3 + クエリ拡張：用語辞書、補完として LLM）も再現できます：`EMBEDDER=bge-m3` と `sweep.py` の構成を使います。

すべてローカル環境で動作します（Ollama、Docker 上の Postgres、GTX 1060 6GB）。Ruri と再ランカーは CPU で動かしています。

### コーパス

**e-Gov 法令検索 API**、分類020「労働」：259件、XML で 34 MB。

日本には単一の労働法典が存在せず、法令が分散しています。労基法が中心ですが、育児休業は育児介護休業法、パワハラは労働施策総合推進法、派遣は派遣法にあります。さらに施行令・施行規則の層があり、法律が「厚生労働省令で定める」と委ねた具体的な内容はそちらに置かれています。

259件から**コア35件**を形式的な規則で抽出しました（14法律＋その施行令・施行規則）。規則では拾えない例外が2件あり、それは手作業で追加しています。コアの区別は別インデックスではなく**チャンクのメタデータのフラグ**として実装したため、ノイズの代償を1回の実行で計測できました。無関係な法令を除外すると **recall@5 が +0.08** 改善します。

### チャンキング

チュートリアルの既定値ではなく、コーパスの分布から設計しました。条文の長さは**中央値と99パーセンタイルで260倍の開き**があります（200文字に対し2,372文字、最大21,157文字）。512トークン固定では9割が中身の薄いチャンクになり、それでも長い条文は途中で切れます。

3段階の方式です。

| 段階 | 規則 | チャンク数 | 割合 |
|---|---|---|---|
| 1 | 項をそのまま | 17,805 | 87.6% |
| 2 | 800文字超の項 → 号で分割 | 2,032 | 10.0% |
| 3 | 800文字超の号 → 文で分割（重複あり） | 325 | 1.6% |

合計 **20,162チャンク**、うちコアは 7,452件です。

各チャンクには文脈を示す接頭辞を付けています（`労働基準法 第三十六条（時間外及び休日の労働）第1項`）。これがないと「前項の協定においては」のように、単独では意味をなさない項が多く残ります。

句点だけで文分割すると、`）`や`」`から始まる断片が生じます。法令文では**括弧の内側にも句点がある**ためです。括弧の対応を条件に加えたところ、誤った分割が167か所なくなりました。

### ストレージ

Docker 上の Postgres 17 + pgvector 0.8.6。ベクトルと全文の索引を同一テーブルに置き、コアの絞り込みは事前フィルタ（`WHERE core`）としています。これにより必ず k 件が返ります。

日本語の全文検索は **Sudachi を DB の外**で使い、分かち書き済みのテキストを格納しています。組み込みの `to_tsvector` では、日本語の条文全体が1つのトークンになってしまうためです。

**HNSW は結果を黙って落とします。** numpy から pgvector に移した際、正解の条文が上位10件から消えました。原因は既定値の `hnsw.ef_search = 40` で、100 にすると全探索と同じ順位に戻りました。索引はエラーも警告も出さず、正解を含まない一覧をそのまま返します。（BGE-M3 では 100 で足りましたが、Ruri に切り替えた後は 200 にしています。下記参照。）

### 日本語固有の問題

英語のコーパスでは生じない層です。

- **語の間に空白がない** → BM25 には形態素解析が必要。Sudachi は分割単位 A（細かい方）を採用。分割単位 C では、有給というクエリが年次有給休暇に一致しません
- **`normalized_form()` は辞書形ではなく正規化表記**です（`する → 為る`、`十 → 10`、`雇入れ → 雇い入れ`）。この表記は法令にもクエリにも現れません。そこで正規化形で品詞フィルタをかけ、索引には表層形を入れています
- **条番号の表記が揺れます**（第39条／第三十九条／第３９条）。正規化は独立したモジュール（`jnum.py`）に置き、正規化した値どうしで比較します
- **条文間の参照**（「法第二十五条第一項の…」）。回答がこの形で挙げた条文は、幻覚でも根拠でもない第三の分類として別に数えています
- **日常語は法令用語と一致しません。** 失業保険は雇用保険法の条文に出現せず、条文は基本手当と書かれています。検索は該当条文を 1 位に出しましたが、同じコンテキストで生成モデルは 10 回中 9 回回答を拒否しました。質問を基本手当に書き換えると 10 回中 0 回でした。プロンプトの一般規則でも解消できましたが代償がありました（「うまくいかなかったこと」を参照）。有効だったのは、検索用辞書が持つ「日常語 → 法令用語」の対応を、質問の後ろに `【用語の対応】` の 1 行として生成モデルにも見せることです
- **クエリの幅違い。** 50 問の摂動コピーで計測しました。全角数字・英字（３６協定）は影響なし（埋め込みモデルが吸収）、半角カナ（ﾊﾟﾜﾊﾗ）は該当 11 問のうち 2 問を落とし、末尾の空白で 1 問を落としました。`fold_query()` が半角カナを全角にし、前後の空白を除きます。NFKC 全体の適用は見送りました。？や（）まで ASCII 化され、コーパスの表記から離れるためです。旧字体・新字体は未計測です
- **インデックスのパラメータはモデルごとに決まります。** Ruri での HNSW 上位 20 件と厳密検索の一致率は、`ef_search` 40 で 0.914、100 で 0.973、200 で 0.998 でした。別のモデルで決めた値のままだと、候補プールの一部が黙って失われます。200 を使用しています

### 用語ヒントと辞書の拡張方法

生成モデルは入力どおりの質問しか見ないため、条文に出てこない日常語（基本手当に対する失業保険など）があると、検索が正しい条文を 1 位に出していても拒否することがあります。`generate.py` の `term_hint()` は、質問を `data/synonyms.json`（手作業で作った「日常語 → 法令用語」27 組）で引き、見つかった各キーの最初の法令用語を、質問の後ろに 1 行として追加します：`【用語の対応】失業保険＝基本手当`。照合は単純な部分文字列判定で、LLM は使わず、遅延も増えません。検索側はこの辞書を使いません（vector モード、拡張なし）。辞書は生成モデルにだけ渡されます。

計測した効果（3 回の実行を 3 回の対照と比較）：過剰拒否が 1 件減り（#22：10 回中 9 回の拒否 → 0 回）、毎回改善した質問が 6 問、毎回悪化した質問が 4 問（#16、#36、#39、#40。#39 は指標の見かけ上の問題）。

拡張するときの手順：

1. 法令用語がコーパスの本文にあることを確認してから追加する（`toc.py`）
2. キー 1 つにつき用語は 1 つ。長いリストは隣の条文に引きずられる（検索で見たのと同じ希釈）
3. 短いキーは長い語の内側にも一致する。追加するキーが触れるすべての質問を確認する（例：健康保険組合の中の組合）
4. 比較は 1 回ではなく 3 回の `--eval` で、前の構成と行う。見るのはカバー率、過剰拒否、取りこぼし時の拒否、質問ごとの悪化リスト。毎回繰り返される悪化は辞書のせい
5. 新しい項目は golden にない質問で検証する。現在の効果は辞書と同じ語彙で測っているため楽観的

## うまくいかなかったこと

この節が最も有用だと考えています。作業の半分は却下した設計であり、いずれも数値を伴って却下しました。

### ハイブリッド BM25 + RRF：recall@5 が 0.18 低下

「ベクトル検索だけでは正確な用語を取りこぼす」という一般論は、利用者が文書と同じ語を使うことを前提にしています。ここでは前提が逆でした。口語の日本語と法令用語が噛み合いません。

| クエリ | BM25 が使える語 |
|---|---|
| 有給って入社してすぐもらえるの？ | 1個 |
| パワハラ対策は会社の義務？ | 0個（条文は「優越的な関係を背景とした言動」） |
| 育休っていつまで取れる？ | 0個（条文は「育児休業」） |

RRF は3問を改善し、**12問を悪化させました**。会社のような一般語で BM25 が50件近い無関係な候補を返し、統合の際にベクトル側の的確な結果と同じ重みを持ってしまうためです。

> **ハイブリッドが有効なのは、二つの手法が別々の質問で失敗する場合です。** ここでは同じ質問で揃って失敗していました。

BM25 の寄与を減らすほど数値が上がるという傾向がはっきり出ています（0.50 → 0.54 → 0.58 → 0.60、完全に切ると 0.68）。

### 検索結果に合わせた golden の拡張

分析の結果、検索失敗とされた6件のうち4件が**自分たちの正解データの不備**でした。golden は法律の条を指しているのに、実務上の答えは施行規則にあるという構図です。

形式的な規則（「施行規則の条は、法第N条という形で明示的に参照していれば同等に扱う」）を書き、50問すべてに適用したところ、候補が193件になりました。多数の親条文を参照する「ハブ」条文を除外すると（労基則第六条の二は16条を一度に参照）83件が残りました。

それでも採用しませんでした。「入社してすぐ有給がもらえるか」という質問に対し、規則は有給休暇中の賃金計算に関する条文を追加してきます。規則自体は正しく適用されているのに、**追加された条文はどれも質問に答えていません**。

> **「X条を具体化している」と「X条について問われたこの質問に答えている」は別の関係です。** 前者はコーパスの構造に符号化されていますが、後者はコーパスの中に存在しません。それは質問の側の性質であり、コーパスは質問を知らないからです。

**golden は意図的に凍結しています。** 指標は構成どうしの比較のためにあり、そのためには正確であることより固定されていることが必要です。

### 検証パスをゲートとして使う

判定モデルを4種類比較しました（qwen3:8b、qwen3.5、gemma4:31b、gpt-oss:120b）。

| | 8b | 3.5 | 31b | 120b |
|---|---|---|---|---|
| 規定の欠落を検出（4件中） | **3** | 0 | 0 | 1 |
| 不適用の引用を検出（8件中） | 7 | 6 | **8** | 7 |
| ブロック率 | 0.65 | 0.65 | 0.65 | 0.80 |

**適用性の検証は機能します。** 正しい条文を引用しているが、その条文が質問された事柄を規律していない、という誤りを捉えられます。**欠落の検証はどのモデルでも機能しませんでした。**

> この課題における判定モデルの精度は**規模の関数ではありません**。8B同士2モデルの差の方が、8Bと120Bの差より大きく出ています。

ゲートとしては使えません。どの判定モデルでも、回答の3分の2が欠陥ありと判定されるためです。

### 構造による欠落検出

モデルで捉えられないため、構造で捉えることを試みました。回答が使っていない項について、再ランカーが「使われた項と同等以上」と評価した場合に欠落とみなす、という規則です。調整可能なしきい値を一切持ちません。

これは原理的な理由で機能しませんでした。**クロスエンコーダは同一条文内の項を区別できません。** 労基法39条の10項すべてが `+0.000 〜 +0.041` の範囲に収まりました。同じ再ランカーが、関連する条文と関連しない条文では `+0.934` 対 `+0.369` と20倍の幅で区別することと対照的です。

モデル側にも再ランカー側にも必要な信号が存在しません。ノイズの上に規則を重ねても意味がないと判断しました。

### 過剰な回答拒否に対するプロンプト規則

根拠条文がコンテキストにあるのに拒否された質問が 2 問ありました。1 問は前提が誤っている質問です（「5年働いたら正社員になれる？」：条文は無期労働契約への転換を定めたもので正社員化ではなく、10 回中 10 回拒否。これは妥当な判断です）。もう 1 問は上記の語彙のずれです。

プロンプトに一般規則（「語彙が日常語で異なるだけなら拒否の理由にしない」）を加えると過剰拒否は 1 件減りましたが、品質が落ちました。主張カバー率は 0.63 → 0.57（旧プロンプトの対照 3 回と新規則 3 回の平均、範囲は重ならない）で、ほかの 4 問で悪化しました。元に戻しました。語彙の問題は、モデルが従う規則ではなく、モデルが見るデータの側で直すほうが適切です。

## 根拠が存在しない場合の回答拒否

独立して計測した項目です。該当する条文がコンテキストに入っていないとき、システムはどう振る舞うか。

検索が実際に外れたのは50問中6問だけで、偶然と区別するには足りません。そこで**アブレーション（統制された除去実験）**を行いました。検索が成功した44問について、正解の条文を候補から強制的に除去し、次点の候補で埋めます。

対応のある設計です。同じ質問で、根拠の有無だけが異なります。「質問の難易度が違う」という説明は構成上排除されています。

| 方法 | 根拠がない時の拒否率 | 誤った拒否 |
|---|---|---|
| プロンプトによるモデルの判定 | 0.25 | 0.00 |
| 再ランカーのスコアしきい値 | 0.18 | 0.05 |
| 両者の統合 | **0.41** | 0.07 |

対応表は完全に一方向で、11件の不一致がすべて同じ向きに出ました（逆向きは0件）。信号は存在しますが弱いといえます。

根拠がない状態で生成された30件の回答のうち、**16件は制度のすり替え**でした。別の法令から正確に引用して答えてしまうという誤りです。最も深刻な例は、労基法20条を除去した状態での「予告なく解雇されたが問題ないか」という質問です。システムは労組法15条（労働協約の解約）から回答し、予告期間を30日ではなく**90日**と伝えました。この回答に対し、自動指標はすべて問題なしと出ています（マーカーは範囲内、引用は有効、架空の参照は0件）。

> **法務用途で危険なのは数値の捏造ではなく、別の規定を正確に、流暢に、自信をもって引用することです。**

モデルの判定とスコアしきい値の統合が単独より優れているのも同じ理屈です。両者は別々の質問で誤ります（18件中、重複は4件のみ）。BM25 とベクトル検索が満たさなかった条件が、ここでは満たされています。

## セキュリティと運用

OWASP Top 10 for LLM Applications（2026年版）に照らして確認しました。

### 間接プロンプトインジェクションの計測

すべての回答にリンクを追加せよ、という指示を含む汚染文書をコンテキストに入れました。プロンプト側の防御（文書をデータとして明示する、区切りタグ、エスケープ）は確率を下げるだけで、どの防御でもモデルは **8 問中 4〜8 問**で指示に従いました。指示の言い回しを少し強めた 1 文で、区切りとエスケープは **8 問中 8 問**突破されました。出力をコードで検査する方式は **32 件中 32 件**を防ぎました。

> **機械的に検査できる種類の害は、モデルへのお願いではなくコードで防ぐべきです。**

検査はドメインの許可リスト（e-Gov、厚生労働省）で、「リンクが出典に含まれるか」ではありません。汚染された出典にはそのリンクが含まれているからです。ドメインだけの表記やメールアドレスも対象です。ストリーミングでは、リンクが完結して検査を通るまで送信を保留するため、途中までのリンクがクライアントに届くことはありません。ただし、リンクは害の一種にすぎず、電話番号や意味の改変は許可リストでは検出できません。そのため、コーパス自体を信頼できる 1 つの情報源に限定しています。

### 運用

- **トレースは既定で内容を記録しません。** すべてのステップを Phoenix + OpenTelemetry でトレースしますが、`TRACE_CONTENT=1` を指定しない限り、質問・プロンプト・回答・ツール引数はマスクされ、長さだけが残ります。このプロジェクトのレイテンシに関する知見は、すべてメタデータだけから得られました。全文のトレースは、ユーザーの質問とエージェントの記憶の保管庫になってしまいます。例外は型だけを記録します。Phoenix は localhost にのみバインドしています
- **API。** CORS ミドルウェアはありません（以前は `*` でしたが不要でした。開発時は Vite のプロキシ経由、ビルド後の UI は同一オリジンです）。リクエストは一度に 1 件で、上限付きの FIFO キューを使います。クライアントには SSE でキュー内の順番が届き、キューが満杯のときだけ 429 を返します。検索はイベントループの外で実行し、再ランキングの途中でクライアントが離脱しても、スレッドが終わるまで枠は確保されたままです。エラーはコードで返し、詳細はログに残します
- **エージェントの記憶**（`agent_graph.py`）は `user_id` ごとに分離しています。`user_id` は必須パラメータで、ファイル名になるため検証しています。スレッドは所有者を記録し、履歴を読む前に照合します
- **バージョン固定**：再ランカーと Ruri は Hugging Face のコミットで固定し（再ランカーのコミットは実行のフィンガープリントに含まれます）、Phoenix はイメージのダイジェストで固定しています

## 評価

### Golden dataset

「質問 → 許容される条文の一覧」50組。キーは `law_id` と条番号です。質問は口語で作成し、条番号は50件すべて条文本文と照合しました。

recall@k は、上位 k 件に**いずれか1つ**の該当条文が入っていれば成功とします。利用者に必要なのは答えであって、網羅的な一覧ではないためです。

### 生成側の指標

- **引用規約** — チャンクごとの `[N]` マーカーと、1行目の `判定: 回答可能 / 回答不可`。50件中50件で遵守
- **引用の妥当性** — 1.000、架空の参照0件。これは品質指標ではなく回帰の見張りとして扱います。モデルは見えているものしか引用できないためです
- **誤った拒否** — BGE-M3 構成で 44 件中 0 件、Ruri では 47 件中 1 件（#24、「うまくいかなかったこと」で触れた前提が誤っている質問）
- **コンテキストの切り詰め** — なし。Ollama は既定のウィンドウを超えるプロンプトをエラーなしで切り詰めます。`check_ctx.py` で確認したところ 50 件中 0 件で、現在はウィンドウを明示的に指定しています（`num_ctx` 32768）
- **回答20件の手動評価** — 独立した3つの観点（実質的に答えているか／内容の歪曲／無関係な素材の混入）

### 3回有効だった手法

自由文から意味を読み取るのではなく、**こちらが管理するトークンをモデルに出力させる**という方針です。

- 条番号ではなくチャンク番号 `[N]`（条番号の書き方はモデル任せだが、チャンク番号はこちらが付ける）
- 拒否を文章の中で表現させるのではなく、1行目の `判定:` として出力させる（それ以前は10通りの言い回しで現れ、明確な拒否は一度もなかった）
- 判定モデルには引用マーカーの一覧を明示的に渡す（自分で読み取らせない）

いずれも、推測に頼る処理を厳密な照合に置き換えられました。

## 注意事項

数値を利用する前にお読みください。

- **`recall@5 = 0.88`（BGE-M3 構成）は自分たちの正解データによって過小評価されています。** 6件の失敗のうち4件は golden の不備であることを手作業で確認済みで、実際の上限は約 0.96 です。計測開始後に正解データを修正しないという方針を取りました。Ruri の 0.94 が、この golden で示せる上限に近いのもそのためです
- **回答20件の手動評価は人間ではなくモデル**（Claude、エージェント経由）が行っています。一次資料を参照した第二の意見であり、人間による基準ではありません
- **4つの判定モデルのうち2つはクラウド実行**です（`gemma4:31b-cloud`、`gpt-oss:120b-cloud`）。それ以外は完全にローカルで動作します
- **生成側の数値はすべて `gemma4:e4b` によるもの**です。モデルを変更すると比較できなくなります
- **golden は50問**です。この規模で 0.02 未満の差はノイズであり、構成選択の根拠にはなりません
- **生成は温度 0 でも決定的ではありません。** 固定した同一コンテキストで、同じ質問が、あるセッションでは 3 回中 1 回、別のセッションでは 10 回中 9 回拒否されました。同一構成の実行間でも主張カバー率は 0.04〜0.08 動きます。そのため構成の比較は 3 回の実行で行い、基準側も対照として再実行しています
- **質問拡張の辞書と生成側の用語ヒントは同じファイルです**（`data/synonyms.json`、27 組）。キーのうち 10 個は golden の質問に一度も現れませんが、50 問のうち 25 問には含まれており、新しい質問での検証は行っていません。この golden 上での効果は楽観的です
- **Ruri 構成の引用妥当性は 1.000 を下回ります**。採用構成では 50 件の回答中に存在しない条文への言及が 2 件あり、3 回の実行すべてで同じ 2 件です（#3、#20）。どちらも本文中の条番号が崩れたもので（例：第六十六条を「第十六十六条」と書く）、`[N]` マーカーの直後のラベルは正しいです。「条番号は見出しの表記のまま書き写す」というプロンプトの 1 行で、もう 1 件（誤ったラベル、#36）は消えました。上記の 50 件中 50 件は BGE-M3 の実行の値です
- **採用構成では項ラベルの誤りが 1 件あります**（#39、3 回の実行すべて）。4 文字の引用「休業給付」が、引用した条の別の項にあるためです。#39 は検索の取りこぼしで、誤った引用というより指標側の偏りに近いものです

## 未解決の課題

- **条文内のどの項を使うかが制御されていません。** 再ランカーは項を区別できず、生成モデルは任意に選び、判定モデルも違いを見ません。対処はパイプラインのより前段にあり、適用される項を明示するよう生成側に要求する形になります
- 条番号を直接含むクエリ向けのルーティング。この場合は語彙一致がベクトル検索に勝りますが、評価用の別データが必要です
- **応答時間。** GTX 1060 で 1件あたり約30秒です（20ペアの再ランキングに約15秒、残りが生成）。高速化の候補は、再ランキング対象を上位20件から10件に減らすこと、量子化クロスエンコーダの導入ですが、いずれも構成が変わるため全面的な再計測が必要になります
- **スコアによる回答拒否ゲートは Ruri では機能しません。** 正解あり・なしの AUC は 0.62 で、取りこぼしの top-1 スコアの中央値（+0.535）が正解ありの中央値（+0.363）より高くなっています。再ランカーが隣接する条文に自信を持つためです。自然な取りこぼしが 50 問中 3 件では再調整できないため、golden の取りこぼしが 10 件以上になった時点で再検討します
- RAGAS による、自前の指標実装との突き合わせ

## 拡張：エージェントのツールとしての RAG

同じ検索をツールとして包み、複数の制度にまたがる質問（「育休中に残業させられる？」は育児休業と労働時間の両方に関わります）に使います。各層が何を加えるかを確かめるため、次の 3 つの形をこの順に作りました。

**`agent.py` — フレームワークなしの素の ReAct ループ。** 何を検索し、いつ十分とするかはモデルが決め、いつ止めるかはコードが決めます。反復回数・トークン・コンテキストの増加・経過時間に予算を設け、さらに繰り返しではなく進捗を測るループ検出を入れました。新しい条文が得られない検索ラウンドは停滞と数え、それが続くとループを止めます。予算が尽きたときは最終ターンを強制し、モデルが使えないときは決定的なフォールバックに切り替えます。ツールのエラーは例外ではなく、モデルが対処できるメッセージとして返します。ツールはまずコアを検索し、再ランカーのスコアが低ければコーパス全体に広げます。`test_agent.py` は、ループ検出と予算を、手作りの入力に対する普通のコードとしてテストします。実際の 4B モデルはループする前に拒否か回答をしてしまい、集合の比較を試すためにわざとループさせるのは順序が逆だからです。

**`agent_graph.py` — 同じエージェントを LangGraph の状態グラフとして。** ループ内の `if` が名前付きのノードとエッジになり、ループにはなかった 3 つのものが得られます。
- **スレッド**：同じ会話の追加質問は状態を共有し、古いツール出力は圧縮されます。結論と条文の一覧は残し、生のテキストは捨てるため、2 問目もコンテキストに収まります
- **ヒューマン・イン・ザ・ループ**：検索が弱いとき、グラフは `interrupt()` で一時停止し、ユーザーに確認を求めます
- **確認付きの長期記憶**：法的な回答を左右するユーザーの事実（都道府県、雇用形態、会社の規模）を発言から抽出し、閉じた選択肢と照合し、推測ではなく本人が述べたことかを確かめたうえで、「はい」の後にだけ保存します。記憶はシステムプロンプトに入るため、そこに書かれたものは再起動後も残るインジェクションになります。閉じた選択肢と確認はそのためです。`user_id` ごとに分離し、90 日を超えた事実は再確認の対象にします。`test_memory.py`

**`mcp_server.py` — MCP 経由のツール。** Claude Desktop に登録してあり、別のモデルが別のループで同じ検索を使えます。トレードオフは明確です。MCP クライアントは独自のループを回すので上記の予算はどれも効かず、ツールが返すテキストは、実際の権限を持つ他のツールがあるかもしれないクライアントに届きます。そちら側の防御はクライアントの責任です。

```bash
uv run python src/agent.py "育休中に残業させられる？"
uv run python src/agent_graph.py              # 対話モード。/mem で記憶を表示、/forget で消去
uv run python src/test_agent.py
uv run python src/test_memory.py
```

⚠️ コーパス全体に広げる分岐はスコアのしきい値に依存していますが、Ruri ではこのしきい値が正解と取りこぼしを分けられなくなっています（未解決の課題を参照）。現在のしきい値では、この分岐はほとんど作動しません。
